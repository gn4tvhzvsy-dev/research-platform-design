Research & Decision Intelligence Platform

Platform Strategy & Design (PSD) — Discussion Draft v0.1

Audience: Development partners and technical/domain SMEs
Date: 24 October 2026
Status: Proposal for review; not an implementation mandate
Scope: Reusable platform capabilities for the existing horse-racing predictor and a future equity-investment research application.

1. Executive decision

We want to engineer a small, production-minded research platform, not assemble a prototype through uncontrolled "vibe coding." Our existing horse-racing predictor and proposed investment research product follow substantially the same process: obtain external data, validate and historize it, derive features, evaluate versioned decision rules, produce explainable recommendations, capture subsequent outcomes, backtest and expose controlled research capabilities to AI clients over MCP.

Proposal: Start with a modular monolith and shared engineering patterns/contracts, while keeping racing and investments as independently deployable domains. Reuse proven components incrementally rather than rewriting the racing predictor. Automate builds, testing and repeatable data pipelines early. Add infrastructure only when a demonstrated requirement makes it worthwhile.

Current known position: Native Swift/SwiftUI iOS client; DuckDB on the backend for analytical data. Other components below are recommendations to validate against the existing codebase, not established implementation facts.

2. Outcomes and principles

Outcomes

  • Reliable acquisition of traceable, point-in-time research data.
  • Reproducible, explainable recommendations, tied to specific input, model/rule and software versions.
  • Safe human-approved modification of research rules through natural language, with measurable historical comparisons.
  • Consistent delivery to iOS, future web apps and authorized MCP clients.
  • A development process that supports AI coding assistants without surrendering engineering controls.
  • Portability between the initial iMac environment and AWS, Azure or GCP.

Engineering principles

  1. Prove value small; engineer boundaries early. Modular monolith before microservices.
  2. Separate domain from platform. Shared contracts and utilities; independent racing and investing rules, data, release decisions and access policies.
  3. Keep decisions reproducible. Preserve input snapshots or references, as-of timestamps, provenance, transformation versions, rule versions and outputs.
  4. Make infrastructure replaceable. Ports/adapters for ingestion, storage, orchestration, authentication, AI providers and client interfaces; avoid premature abstractions without a second implementation or plausible migration need.
  5. Data quality is a release gate. Bad, stale or incomplete data must be visible and block publication where material.
  6. Deterministic execution; probabilistic assistance. LLMs propose and explain; validated rules and Python execute decisions.
  7. Security and operability by default. Least privilege, secrets management, monitoring, backups, restoration tests and incident runbooks.
  8. Humans authorize consequential changes. Agents are user-triggered, bounded and auditable; never silently publish strategies or deploy production.

3. Scope

MVP scope

  • One vertical slice in the existing racing domain, from source import to immutable recommendation record, outcome capture and reproducible replay.
  • Define and prove shared interface contracts usable by a second domain (investment research), without forcing premature generalization.
  • Backend DuckDB analytics; persisted, versioned source datasets (Parquet where helpful).
  • API endpoints for current and historical recommendations with explanations.
  • Read-only, scoped MCP research tools using the same application services as the API.
  • CI checks, repeatable local setup, deployment scripts, logs/metrics and basic backups.
  • Rule definitions maintained in code/config initially; prototype the natural-language workbench only after versioning and replay are proven.

Not in MVP

  • Live trading, auto-placement of bets/orders, autonomous rule promotion or autonomous production deployment.
  • Multi-cloud active/active infrastructure, Kubernetes, a generalized plugin marketplace or large microservices landscape.
  • Full public multi-tenant launch, polished web workbench, and comprehensive LLM workflow orchestration.
  • Migrating the entire existing predictor before extracting a proven slice.

Airflow decision: Airflow is attractive for daily ingestion, dependency management, retries, backfills and pipeline operations. Its metadata store is separate from analytical DuckDB.

6. Shared data and decision contracts

Define schemas and stable identifiers for:

  • Source event/batch: provider, source key, fetch time, provider publication time, effective time, raw artifact checksum and license/usage constraints.
  • Canonical observations: domain/entity identifier, measure, value, units, validity period, available-at timestamp, quality flags and source references.
  • Derived features: feature name/version, inputs and source lineage, as-of time, execution version and reproducibility metadata.
  • Rule/strategy: immutable version, author, review state, parameter schema, rationale, test evidence and effective dates.
  • Recommendation: entity, as-of time, run ID, strategy version, score/band, reasons, risk flags, data-quality state and publication timestamp.
  • Outcome: observation horizon, relevant result/return, timestamp and measurement definition.
  • Evaluation: dataset snapshot, splits/windows, metrics, benchmark, known limitations and run artifacts.

Use temporal semantics rigorously: event time, published/available-at time, ingestion time and decision as-of time are not interchangeable. Backtests must not use data that was unavailable when the simulated decision was made. Record corrections/restatements rather than silently overwriting history.

7. Typical workflows

Scheduled data-to-recommendation

  1. Trigger ingestion of source datasets (schedule or event).
  2. Land raw immutable/source-traceable files and metadata.
  3. Validate structure, freshness, completeness, duplicates and domain invariants; quarantine defects.
  4. Normalize and derive features with code and input versions attached.
  5. Run the approved strategy on a known point-in-time dataset.
  6. Persist immutable recommendations and explainability/evidence; publish only if quality gates pass.
  7. Expose via iOS API and read-only MCP tools; capture outcomes when known.
  8. Track job performance, failures, freshness and recommendation coverage.

SME-driven rule change

  1. SME describes intended change in natural language.
  2. LLM proposes a typed rule/configuration diff and human-readable interpretation; no free-form executable code is activated.
  3. Schema validation, policy checks and reproducible regression/backtests run against a frozen dataset.
  4. Compare current and proposed strategy using predefined metrics, out-of-sample periods and risk/failure analysis.
  5. Authorized reviewer approves/promotes immutable version; rollback points remain available.
  6. Full audit trail records who proposed, reviewed, approved and activated the change.

Complex code changes use normal feature branches, pull requests and CI rather than bypassing development controls.

8. Backtesting and evaluation discipline

  • Version input data, evaluation code, feature definitions and strategy config; fix seeds where applicable.
  • Use time-ordered/walk-forward evaluation rather than random leakage-prone splits.
  • Establish a baseline and repeatable performance metrics appropriate to each domain.
  • Include transaction costs/slippage for investment research when relevant; account for changing odds/market availability in racing.
  • Guard against look-ahead bias, survivorship bias, restatements, overfitting and cherry-picked results.
  • Report calibration, coverage, missing-data behavior and drawdowns/variance alongside headline returns or hit rates.
  • Maintain a locked holdout dataset and explicit criteria for promoting a new strategy.

9. MCP and AI integration

MCP should be an access surface over stable application services, not direct privileged database access. Example authorized read-only tools:

  • get_recommendations(domain, as_of, filters)
  • explain_recommendation(domain, recommendation_id)
  • get_data_lineage(domain, entity_id, as_of)
  • compare_strategy_runs(domain, baseline_id, candidate_id)
  • get_backtest_report(domain, run_id)
  • get_data_quality_status(domain, dataset_id)

Requirements: authenticate/authorize each caller; tenant/domain permissions; bounded query sizes; rate and cost controls; detailed audit logs; sensitive-data filtering; prompt-injection-aware handling of external content. Any tools to launch tests or propose changes must be segregated from read-only tools and gated by explicit authorization. No MCP tools for live trading in the initial scope.

10. AI-assisted software delivery controls

Permitted workflow: Developer manually requests Cursor/Codex work → bounded issue/acceptance criteria → agent branch → tests/lint/security checks → pull request → human review → approved merge → gated deployment. No self-initiated agents.

Repository standards:

  • main protected; PR mandatory; required status checks; CODEOWNERS for rules, schema, security and deployment changes.
  • Short-lived feature branches; small PRs; conventional change descriptions and tests.
  • Unit, integration, contract, data-quality and golden-dataset regression tests.
  • Ruff/type checks (or equivalent), SwiftLint/Swift tests, dependency and secret scanning.
  • Reproducible lockfiles/builds; versioned migration and rollback procedures.
  • Environments: local/dev first; staging and production before public launch.
  • Database backup/restore exercises; performance and recovery objectives defined before scale.
  • AI-generated changes are treated as untrusted submissions and reviewed on the same basis as human changes.

Definition of done (MVP): Acceptance criteria met; automated tests passed; reproducibility verified; relevant documentation/ADR updated; logs/diagnostics added; secret and dependency checks passed; deployment and rollback proven.

12. Delivery increments and exit criteria

Phase 0 — Discovery and baseline (1–2 weeks indicative)

  • Map current racing predictor modules, jobs, DuckDB schemas, deployment, tests and MCP endpoints.
  • Record baseline: ingestion reliability, daily runtime, test coverage, reproducibility, manual steps and known data-quality gaps.
  • Agree the domain boundaries, target first vertical slice and quality attributes.
  • Create initial ADRs and a prioritized technical backlog. Exit: Existing end-to-end journey documented; no architecture decisions based on assumptions about unseen code.

Phase 1 — Production-minded vertical slice

  • One racing source through ingestion → quality gate → feature → approved rule → immutable recommendation → result → replay → API/MCP.
  • Add baseline CI, local one-command setup, tests, observability and documented recovery. Exit: A developer can recreate and rerun the result from a known snapshot; failures surface clearly.

Phase 2 — Workflow reliability and reuse

  • Time-box Airflow 3 proof of concept for scheduled ingestion/backfills; compare simple cron/worker and Dagster/Prefect against operational criteria.
  • Extract only the contracts and components demonstrated reusable by the racing vertical slice.
  • Add dependency-aware jobs, retry/idempotency discipline and data-quality dashboards. Exit: One-click/history-backed reruns, reliable backfills and an explicit orchestrator ADR.

Phase 3 — Investment proof of reuse

  • Add one bounded investment dataset and one transparent scoring methodology supplied by the domain SME.
  • Implement with shared contracts while retaining separate domain rules, datasets and authorization.
  • Compare implementation effort and coupling to validate actual reuse. Exit: Second domain proves platform seams without changing racing business semantics.

Phase 4 — Controlled AI rule workbench

  • Prototype natural-language-to-validated-rules using a constrained schema.
  • Run candidate vs baseline backtests and require reviewer approval to publish.
  • Trial SME usability with JupyterLab/marimo and a minimal web interface before committing to Next.js. Exit: Every published rule change is inspectable, testable, reversible and attributed.

Phase 5 — Public readiness, if justified

  • Identity and authorization, transactional database if required, tenant isolation, security reviews, license/compliance review, scalable hosting, public API protections and iOS release pipeline.
  • For Australian public investment recommendations or trading integration, obtain qualified financial-services legal/compliance review before launch. Exit: Operational, security and regulatory release gates satisfied; no automated financial execution by default.

13. Non-functional requirements to set early

Set measurable targets in discovery rather than inventing them now:

  • Correctness: critical scoring regression tests and immutable audit trail.
  • Freshness: per-source data age limits and stale-data handling.
  • Reproducibility: ability to replay a specified recommendation to the same result under pinned inputs/code/rules.
  • Availability/recovery: agreed RPO/RTO with backup and restore validation.
  • Performance: latency budgets for read APIs vs asynchronous heavy research.
  • Security/privacy: least privilege, encryption, retention, data license compliance and separation of environments.
  • Cost: per-environment infrastructure spend, LLM usage budgets and per-run compute visibility.
  • Portability: deployment instructions that work locally and on at least one target cloud without domain code changes.

15. Initial ADRs and open questions for partner review

  1. What does the racing predictor actually run today: backend language, job scheduler, infrastructure and dependencies?
  2. Can we demonstrate a fully reproducible recommendation using existing code/data without major refactoring?
  3. Which data quality defects most often invalidate a prediction?
  4. How much data, how frequently updated, and how many concurrent readers/writers do we anticipate in 12 months?
  5. Should racing and investing remain separate repositories/deployments, with shared packages, or live in one monorepo initially?
  6. Is Airflow's history/backfill/control surface worth the extra metadata DB and processes at current scale?
  7. What access and commercial-use rights do our racing and financial data feeds permit?
  8. Which AI/MCP clients need access, and what capabilities must remain read-only?
  9. What constraints and approval rights must the domain SME have when changing models?
  10. What are the agreed operational SLOs, spend ceiling and first cloud deployment target?

16. First partner working session: proposed decisions

Agree (a) the first racing vertical slice, (b) minimum shared contracts, (c) repo/build/test conventions, (d) point-in-time/reproducibility acceptance test, (e) the Airflow spike decision criteria, and (f) owners for architecture, data quality, SME sign-off and release approval.

Bottom line: Treat AI tools as accelerated contributors within an engineering discipline. Build one reliable evidence-to-recommendation flow, then reuse it carefully across domains. Prefer well-defined contracts, observability, tests and reversible decisions over early infrastructure sophistication.
